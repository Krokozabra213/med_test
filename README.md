# Task Service

Сервис для управления задачами с HTTP API на Go.

## Требования

- Go `1.23+`
- Docker и Docker Compose

## Быстрый запуск через Docker Compose

```bash
docker compose up --build
```

После запуска сервис будет доступен по адресу `http://localhost:8080`.

Если `postgres` уже запускался ранее со старой схемой, пересоздай volume:

```bash
docker compose down -v
docker compose up --build
```

Причина в том, что SQL-файл из `migrations/0001_create_tasks.up.sql` монтируется в `docker-entrypoint-initdb.d` и применяется только при инициализации пустого data volume.

## Что добавлено в рамках задания

Маршруты:

- `GET /api/v1/rules`
- `GET /api/v1/rules/{id}`
- `PUT /api/v1/rules/{id}`
- `DELETE /api/v1/rules/{id}`

В сервис добавлена поддержка **периодических задач**.

Вместо хранения периодичности внутри самой задачи используется отдельная сущность — **правило периодичности**.
Задача в таблице `tasks` является конкретным экземпляром задачи, а правило описывает, **когда и как такие задачи должны генерироваться**.

Это позволяет:

- не раздувать основную таблицу `tasks`;
- отделить “шаблон” от конкретных инстансов задач;
- изменять правило независимо от уже созданных задач;
- добавлять новые типы периодичности без изменения уже существующей логики воркера.

Периодические задачи создаются **фоновым воркером**:

- по тикеру воркер загружает список правил;
- для каждого правила выбирается подходящий обработчик;
- обработчик определяет, должна ли задача быть создана для текущей даты;
- если да — создаётся обычная запись в `tasks`.

Для каждого типа периодичности используется отдельный handler.
Воркер не содержит логики конкретных правил — он только:

- получает список правил;
- находит обработчик по типу;
- запускает обработку.

Таким образом, добавление нового типа периодичности сводится к:

1. созданию нового handler;
2. регистрации его в `main`.

Существующий код воркера при этом не меняется.

## Поддерживаемые типы периодичности

На текущий момент реализованы следующие типы правил:

### `daily`

Создание задачи каждые `N` дней.

Пример `settings`:

JSON

```
{
  "interval": 2
}
```

### `monthly`

Создание задачи в определённый день месяца.

Пример `settings`:

JSON

```
{
  "day": 15
}
```

### `specific_dates`

Создание задачи только в конкретные даты.

Пример `settings`:

JSON

```
{
  "dates": ["2026-05-01", "2026-05-09", "2026-06-12"]
}
```

### `day_parity`

Создание задачи по чётным или нечётным дням месяца.

Пример `settings`:

JSON

```
{
  "parity": "even"
}
```

## Принятые допущения

Так как задание намеренно оставляет часть требований открытыми, были приняты следующие допущения.

### 1. Изменение правила не изменяет уже созданные задачи

Если правило было изменено, это влияет только на **будущие** сгенерированные задачи.
Уже существующие задачи сохраняются как самостоятельные сущности.

**Почему так:**
иначе изменение правила могло бы неявно менять пользовательские данные и ломать ожидаемое поведение.

### 2. Удаление правила не удаляет уже созданные задачи

Сгенерированные ранее задачи считаются обычными задачами и продолжают существовать даже после удаления правила.

**Почему так:**
созданная задача уже является бизнес-сущностью сама по себе и может быть отредактирована пользователем независимо от правила.

### 3. Время расчёта периодичности зависит от `timezone`

Для каждого правила хранится timezone, и проверка “нужно ли создавать задачу” выполняется в локальном времени этого правила.

**Почему так:**
иначе периодические задачи для разных регионов будут создаваться в неверный момент.

### 4. Генерация выполняется по текущему дню, без исторического backfill

В текущей реализации воркер проверяет, должна ли задача быть создана **на текущую дату**.
Если сервис был недоступен несколько дней, пропущенные задачи задним числом не восстанавливаются.

**Почему так:**
для тестового задания выбран более простой и предсказуемый вариант без дополнительной логики догенерации исторических инстансов.

### 5. Начало отсчёта для некоторых правил — момент создания правила

Для правил вида `daily` базовой точкой отсчёта считается дата создания правила (`created_at`), если иное явно не задано.

**Почему так:**
это позволило не вводить дополнительное поле вроде `starts_from` и сохранить модель проще.

### 6. Формирование настроек для `monthly` на стороне клиента

Для типа периодичности `monthly` предполагается, что клиент (фронтенд) самостоятельно извлекает нужное число месяца из выбранной пользователем даты и передает его явно в поле `settings` в формате `{"day": X}`.

**Почему так:**
Это делает API более прозрачным. Бэкенд не пытается угадать намерения пользователя, неявно вычисляя параметры из других полей. Клиент явно передает те настройки расписания, которые были выбраны на UI, а бэкенд отвечает только за их валидацию и исполнение.


## Валидация `settings`

Поле `settings` хранится в `JSONB`, а конкретная структура зависит от `recurrence_type`.

Для каждого типа правил используется отдельная структура настроек и строгий JSON decode с запретом неизвестных полей.

Пример: если для `daily` ожидается

JSON

```
{
  "interval": 2
}
```

то payload вида

JSON

```
{
  "intervadl": 2
}
```

считается невалидным.

**Почему так:**
это защищает от “тихих” ошибок ввода и делает API предсказуемее.


## Защита от дублей

Для периодически сгенерированных задач используется уникальность по сочетанию:

- `recurrence_rule_id`
- `scheduled_at`

Это гарантирует, что одна и та же задача по одному и тому же правилу на одно и то же время не будет создана дважды.

Дополнительно это делает воркер безопасным при повторных тиках.

## Граничные случаи, которые учтены

- повторный тик воркера не создаёт дубль задачи;
- неизвестный тип периодичности не валит весь воркер, а логируется как ошибка для конкретного правила;
- при создании задачи с правилом используется транзакция, чтобы исключить создание только одной сущности.
- невалидный `timezone` приводит к ошибке обработки конкретного правила;
- невалидный JSON в `settings` приводит к ошибке только по конкретному правилу;
- `specific_dates` валидирует формат дат;
- `day_parity` работает по чётности дня месяца;
- `monthly` учитывает логику конкретного дня месяца;
- если текущее время ещё не достигло `scheduled_time`, задача не создаётся раньше времени.


## Ограничения текущей реализации

В рамках тестового задания сознательно не реализовывались следующие вещи:

- историческая догенерация пропущенных задач после простоя сервиса;
- сложные составные расписания уровня cron / RRULE;
- distributed locking между несколькими экземплярами воркера;
- массовое редактирование уже созданных задач после изменения правила;
- отдельный механизм paused / archived / disabled правил, если он не требуется бизнес-логикой.

## Почему выбран именно такой подход

Потому что он даёт хороший баланс между:

- `tasks` остаётся таблицей конкретных инстансов задач и не смешивается с шаблонами;
- правило можно изменять независимо от уже созданных задач;
- новые типы периодичности добавляются через новый handler без изменения логики воркера;
- `settings` в `JSONB` позволяет хранить тип-специфичные параметры без раздувания схемы;
- генерация задач сделана идемпотентной за счёт уникальности `(recurrence_rule_id, scheduled_at)`.

## Возможные направления развития

Если развивать решение дальше, я бы добавил:

- `starts_from` / `ends_at` для правил;
- флаг активности правила (если в отпуске то нужно поставить `is_active=false` чтобы задачи не создавались);
- фильтрация задач по полям (`scheduled_at`, `status`)
- пагинация задач через `limit`, `offset`
- поддержку `weekly`;
- backfill пропущенных задач;
- метрики воркера и health/readiness checks;
- интеграционные, unit тесты.
- добавить логику создания правила `monthly` для `day=31`, тогда задача будет создаваться для каждого последнего дня месяца

### В рамках ограниченного времени основной акцент был сделан на проектировании функциональности и корректности сценариев. Автоматические тесты не были добавлены, но архитектура сервиса позволяет покрыть отдельно handlers, worker и repository слой.
